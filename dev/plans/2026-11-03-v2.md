# Zapret v2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** повысить устойчивость обхода и уменьшить измеренную стоимость обработки, обеспечив проверяемый выбор стратегии и восстановление после сбоев.

**Architecture:** оставить официальный winws2/Lua и совместимое PowerShell-управление. Выделять из lib.ps1 небольшие компоненты с явными контрактами: снимок окружения, описание итоговой конфигурации, измерение/выбор, управление/восстановление. Сохранять существующие функции как совместимые оболочки до миграции вызывающего кода.

**Tech Stack:** Windows PowerShell 5.1, .NET Framework, официальный zapret2 v1.0.6 как стабильная база, Lua; существующие PowerShell/Python-тесты. Новые бинарные зависимости требуют отдельного обоснования.

**Spec:** `dev/research/2026-11-03-v2-review.md` — исследование, подтверждённые пробелы, требования и границы.

## Global Constraints

- База для сравнения — v1.9 / `23c14e6ae6f9c2fa5a776d37a98bdc09c5c80452`.
- PS5.1, BOM для PowerShell, сохранение принятой кодировки/окончаний строк; dev-файлы исключаются из пользовательского ZIP.
- Пользователь использует Wi-Fi. Кабель и изменение роутера/NIC не являются условием улучшения.
- Открытая игра запрещает фоновые перезапуски. Исследовательские тесты по умолчанию выполняются на временных копиях, без живого WinDivert-перехвата.
- Не менять стабильную версию/бинарники и не публиковать v2 до завершения этапов приёмки. Живые A/B-сеансы выполняются отдельным явно обозначенным этапом.
- Никаких обещаний уменьшения игрового пинга по результатам HTTPS-тестов; численные цели задаются после baseline.
- Не публиковать runtime, SSID, внешние IP, PAC-URL и секреты. Локальный сетевой ключ не требует внешнего geo-IP запроса.
- Сохранять настройки, пользовательские списки и происхождение заимствованного кода. Не объединять несовместимые условия участников circular.

## Review Focus

- Сеть/списки меняются во время измерения: результаты не применяются к новому состоянию (задача 1).
- Наблюдение невозможно из-за прав/тайм-аута: сохраняется Unknown, а не ложный Closed/Offline (задача 2).
- Две стратегии имеют одинаковое имя, но разные условия/байты: не разделяют один fingerprint и неподходящий круг (задача 3).
- Поздняя стратегия выигрывает только из-за временного улучшения Wi-Fi: контроль дрейфа выявляет недостоверное сравнение (задача 4).
- Позднее внедрение нового формата не должно потерять старые пользовательские данные: сначала shadow-режим и точная резервная копия (задачи 1–4).

## Alpha1: достоверная конфигурация и измерения

### Задача 1. Неизменяемый снимок всех входов

Файлы: создать `tools/netstate.ps1`, `tools/recipe.ps1`, `dev/tests/contexttest.ps1`; изменить `tools/lib.ps1`, `tools/test.ps1`, `dev/tests/run-all.ps1`.

Контракты:
- `Get-NetworkObservation` возвращает `ObservedUtc`, `Known`, локальные идентификаторы активных интерфейсов, маршруты/режимы IPv4/IPv6, состояние DNS/прокси/TUN. Сырые данные остаются локальными; состояние ошибки не равно пустой сети.
- `Get-RunSnapshot -Settings -StrategyIds -Targets -NetworkObservation` возвращает `SchemaVersion`, `ContextKey`, `ConfigHash`, `Generation`, manifest реально используемых файлов и нормализованные настройки. Включить содержимое списков/исключений, blobs, Lua, бинарников и выбранных профилей; порядок hostlist-правил сохраняется там, где влияет на смысл.
- `Test-RunSnapshot -Before -After` возвращает `Compatible` и коды причин; не меняет файлы/процессы.

- [ ] Написать регрессии: одинаковый ввод стабилен; новый публичный DHCP-IP сам по себе не меняет контекст; новая Wi-Fi-сеть/TUN/значимый маршрут меняет поколение; одинаковый ASN не объединяет разные контексты.
- [ ] Добавить проверки изменения только списка, blob, исключения и стратегии с прежним ID/названием; snapshot, собранный во время изменения файла, не принимается как целостный.
- [ ] Реализовать snapshot на согласованной копии входов. Ключ неизвестной сети не должен превращаться в один общий доверенный ключ для всех неизвестных сетей.
- [ ] Встроить shadow-снимки в отчёт теста; прежнее ранжирование пока сохраняется. При несовместимости запрещать запись/применение результата.
- [ ] Прогнать contexttest, historytest, retrytest, astlint/check. Ревью, отдельный коммит.

### Задача 2. Единая диагностика состояния сети

Файлы: `tools/netstate.ps1`, `tools/lib.ps1`, `tools/menu.ps1`, `tools/report.ps1`; расширить `dev/tests/proxytest.ps1`, создать `dev/tests/netstatetest.ps1`.

Контракт: наблюдение порта/подключения содержит `State`, `ObservedUtc`, `Evidence`, `OwnerPid`/`OwnerStartTime` при доступности. Состояния настройки и доступности разделены. Транспортная готовность не доказывает успешный HTTP/SOCKS-запрос.

- [ ] Воспроизвести несовпадение таблицы сокетов с доступным loopback-слушателем в путях Telegram и proxy-stuck, а не только Get-ProxyWarnings.
- [ ] Добавить fixture: geo-IP недоступен, контрольный HTTPS доступен; нет прав на маршруты; PAC/WPAD; порт принадлежит другому клиенту; PID использован повторно.
- [ ] Переиспользовать bounded loopback-проверку 1.9; не выполнять DNS/запросы к внешним proxy endpoints. Не считать ошибку наблюдения доказательством отключения.
- [ ] Перевести потребителей на общий снимок. Инвалидировать кэш HTTPS при смене поколения сети без автоматического перезапуска обхода в игре.
- [ ] Проверить TTL кэша, ротацию событий и редактирование экспортируемых данных. Ревью, отдельный коммит.

### Задача 3. Контракт профиля и проверяемый импорт Flowseal

Файлы: создать `tools/strategy-schema.json`, `dev/tests/profiletest.ps1`, каталог `dev/fixtures/flowseal-1.10.4/`; изменить `dev/flowseal2zapret2.py`, `tools/recipe.ps1`, `tools/lib.ps1`, README и notices при необходимости.

Контракт профиля: `Source` (repo/tag/file), `Match` (L3/L4/L7, направления, порты, списки/исключения), `Actions`, `Dependencies`, `Capabilities`, `CompatibilityNotes`. `ConfigHash` строится из реальной собранной конфигурации. Неизвестные опции импорта — ошибка с исходным контекстом.

- [ ] Зафиксировать входы 22 стратегий Flowseal1.10.4 и контрольные суммы, сохранив лицензию; сначала тест IPv4-only ALT5, который текущий перенос не сохраняет.
- [ ] Покрыть границы `--new`, условия IPSet/hostlist, L3/L7 и исключения. Для реально несовместимых возможностей требовать явное описание различия, не молчаливое удаление.
- [ ] Реализовать каноническую модель и сборку; сохранить чтение прежних strategies/alt*.txt через адаптер. Не изменять вручную пользовательские профили при чтении.
- [ ] Разделить несовместимые круги либо отклонить недопустимое объединение. Проверить, что добавление IPv4-only участника не отключает IPv6 у остальных.
- [ ] Прогнать profiletest, lintstrat, drystrat, retrytest, luatest при доступных правах; сравнить генерируемые правила с утверждёнными различиями. Ревью, отдельный коммит.

### Задача 4. Стенд сравнения с v1.9 и доказательный выбор

Файлы: создать `dev/perfbench.ps1`, `dev/tests/selectiontest.ps1`, `tools/selection.ps1`; развивать `dev/strategylab.ps1`, `tools/test.ps1`, `tools/recipe.ps1`.

Контракты: результат пробы хранит все попытки, источник/время, DNS/TCP/TLS/HTTP, байты, timeout, конфигурацию и generation. План A/B хранит seed и порядок. Оценка возвращает пригодность, причины отказа, неопределённость, доступность по обязательным группам и стоимость; не сводит неизвестность к нулю.

- [ ] Написать синтетические тесты постоянного качества, временного дрейфа, редких потерь и улучшения только со второй попытки. Проверить, что отсутствие обязательного сервиса нельзя компенсировать множеством второстепенных успехов.
- [ ] Реализовать отчёт CPU-time/private bytes и измерения холодного/тёплого интерфейса; локальные fixture-пробы не перехватывают пользовательский трафик.
- [ ] Добавить seed-план A/B/B/A и контрольный A/A-режим. P95/P99 выводить только с достаточной выборкой; сохранять число наблюдений.
- [ ] Сначала shadow-ранжирование и сравнение с v1.9. Подготовить отдельный сценарий живого Wi-Fi A/B, параметры нагрузки и критерии остановки при игре/смене сети.
- [ ] Предусмотреть финальный replay точной рабочей конфигурации вместо тестового IPSet any. До реализации координатора следующего этапа не включать автоматическое применение нового алгоритма.
- [ ] Ревью стенда и результатов синтетики; отдельный коммит. По baseline определить численные цели производительности.

## Следующие этапы: отдельные планы перед реализацией

- **Alpha2:** общий mutex/владелец службы между папками; идентификация операций; Job Object/heartbeat для тестов; журнал транзакций с аварийным восстановлением; последняя рабочая конфигурация. Принудительно завершать только тестовые процессы на изолированном стенде.
- **Beta:** быстрый отсев семейств, pacing, финалисты в рабочем режиме; TTL/LRU контекстной памяти, ограниченная запись состояния; измеренное сужение перехвата и бюджет фейков. До/после сравнивать с v1.9 на одинаковых сценариях.
- **Экспериментальный канал:** QUIC-feedback и upstream UAF-fix. Сначала проверить API совместимость и возможность воспроизводимой сборки, затем отдельные протокольные/нагрузочные тесты. Не подменять официальный бинарник незаметно.
- **Stable2.0:** миграция1.9→2.0 и откат, длительный прогон, сон/пробуждение/сменаWi-Fi/TUN, опубликованные границы проверки; CI и проверка содержимого ZIP.
